# Migrate to Plugin UI/API v1.1

The redesigned host requires an explicit **1.1.0** contract in both
`manifest.json` and `ui.json`. Keep `manifest_version: 1` and `schema_version:
"v1"`; the wire major and `.utp` format remain unchanged.

Add `"api_contract_version": "1.1.0"` to both documents and use
`"sdk_version_range": "^1.1.0"` in the manifest. The SDK exposes
`API_CONTRACT_VERSION = "1.1.0"`. Plugin release versions are separate: a plugin
may release `2.4.0` while targeting contract `1.1.0`.

Missing declarations remain v1.0.0. Ranges such as `*` and `^1.0.0` do not certify
migration. Review and test actual backend and UI behavior before declaring the
new contract. The source validator requires maintained examples and official
plugins to declare v1.1 explicitly, and package validation checks that the UI
declaration matches the manifest.

The host stops the **whole installed legacy plugin**, including backend workers,
gateway calls, actions, routes, UI and PWA contributions. It keeps installation
identity, data, settings and recorded grants. A compatible verified update uses
the existing permission review and transaction flow; unchanged grants remain,
and additional permissions require approval. A legacy rollback target cannot
execute on the new host. Core application pages remain available.

Build a new release with the existing builder and preserve published archives,
signatures and history. The v1.1 declaration is bound by the signed manifest.
Run source/package validation, the actual host contract check and real-worker
lifecycle tests. Check desktop/phone, light/dark, failure, update and uninstall
behavior. See [manifest compatibility](manifest.md) and
[lifecycle conformance](../testing/lifecycle.md).

The official PWA migration uses plugin release **0.0.2** around reviewed mobile
assets at **0.0.2**. The neutral offline page follows the device's validated
Light, Dark, System and personal palette settings without caching account data.
Exact asset bytes, hashes and provenance remain validated. Plugin and source
versions remain separate and 0.0.x; stable promotion requires a human release decision.

The new [Home Widgets demo](https://github.com/obsoletelabs/unnamed_tracking_app_plugins/blob/main/examples/home-widgets/README.md) source
registers a useful Library glance widget and an Embedded media demo widget.
`frontend.home.widgets` authorizes optional Home registration independently of
native JavaScript and data scopes. Widgets declare desktop/phone page IDs and
non-secret personal configuration fields. The host saves those options to each
account, withdraws live content on disable/revocation, and retains selections
for restoration. See the host's
[widget contract](https://github.com/obsoletelabs/unnamed_tracking_app_2/blob/main/wiki/docs/development/plugin-home-widgets.md)
for the exact current API. No embedded media visual may enter PR evidence.

## Palettes and themed controls

The `examples/theme-palettes` source contributes Blue Hour through the separate
low-risk `frontend.themes` permission. It requires no native JavaScript or data
permissions. Each palette supplies eleven semantic color roles for both light
and dark mode. Applying it makes an editable personal copy that survives plugin
withdrawal. See the host's
[palette contract](https://github.com/obsoletelabs/unnamed_tracking_app_2/blob/main/wiki/docs/development/plugin-themes.md).

Bundled frontends receive the reviewed `sdk/frontend_appearance.js` and CSS as
`frontend/appearance.js` / `frontend/appearance.css` in their package. Include
them in the entry HTML before your plugin's controls. The bridge accepts only
its parent and the v1.1 cosmetic snapshot; native components inherit `--ui-*`
tokens and can use `host.appearance()` / `host.onAppearanceChange(callback)`.
Keep original rendered document/media colors while theming surrounding controls.

Document Browser keeps its opaque document renderer and adds a native Settings
page for preview limits. This adds explicitly reviewed `frontend.native`,
`frontend.settings` and `frontend.navigation.settings` permissions; old grants
do not silently approve them. Disposing the native page ignores late responses.

The two new examples are explicitly listed in `catalogue.json.unreleased_plugins`.
They are built and validated in previews but do not claim a published trusted
release in the retained catalogue. Publication uses the existing signed release
workflow with new versions; historical archives and records remain byte-identical.
